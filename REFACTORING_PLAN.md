Grammar (binding; a builder must not read "confirm" as "the word confirm anywhere"):
* `first_line(text)` = the first line of `text` whose `strip()` is non-empty (or `""`). `is_word(line, word)` = `line.strip()` ASCII-only, `casefold()` equals `word`, after removing trailing punctuation from the set `. ! , ;` (leading text, a second word, `please`, a quote marker `>` or any other character makes it False; no Unicode folding, so look-alike letters never match).
* **cancel** = `is_word(first_line(view.typed_text), "cancel")` when `view.confident`, OR (fail-safe, an action that can only stop a payment) `is_word(view.raw_first_line, "cancel")` even when `view.confident` is False.
* **confirm** = `view.confident` AND `is_word(first_line(view.typed_text), "confirm")`. `view.raw_first_line` is NEVER used for confirm; when `confident` is False `typed_text` is `""`, so confirm is impossible.
* **ambiguous** (evaluated FIRST): the CONFIDENT typed text contains BOTH words `cancel` and `confirm` anywhere (word-bounded, case-insensitive, `(?<![A-Za-z0-9])(cancel|confirm)(?![A-Za-z0-9])`) -> `"ambiguous"` (a no-op, audited `command_ambiguous` by S11). Quoted, forwarded and subject text are never inspected (they are not in `typed_text`).
* Otherwise `None`. Result precedence: ambiguous, then cancel, then confirm, then None. Examples: `confirm` -> confirm; `Confirm.` -> confirm; `cancel!` -> cancel; `do not confirm, the amount is wrong` -> None; `Cancel please` -> None; `please cancel this` -> None; `cancel\nconfirm` -> ambiguous; `thanks\nconfirm` -> None.

## 2a. State and transition table - the single source for the 0013 CHECK list, `TRANSITIONS`, and S11

This table is frozen BEFORE S9; S9's SQL, `instructions.TRANSITIONS`, both stores and S11 are derived from it. Time bases: "fresh" means `now - received_at <= PAYMENTS_MAX_MESSAGE_AGE_HOURS` (default 24), EXCEPT for an `accepted` row (R4-T3), whose freshness base is `coalesce(accepted_at, received_at)`: `accepted_at` is set once when a row enters `accepted` from `awaiting_confirmation` (the CONFIRM mail's trusted receipt time), and is null for a row accepted directly on the immediate path (its base is then its own `received_at`). `received_at` is the trusted receipt time: the IMAP `INTERNALDATE` and the topmost `Received` header timestamp are both read, and when both exist the OLDER of the two is used (stricter), when only one exists that one is used, when neither exists the message fails closed (`expired_age`); the `Date` header is never used.

**Sweep order (per cycle, per row, binding).** (1) `recover_stale_submitting`; (2) for every non-terminal row the EXPIRY check comes FIRST (age for `accepted` by `coalesce(accepted_at, received_at)`, awaiting expiry, confirm expiry, held expiry): an expired row becomes `expired` and nothing else is evaluated for it; (3) only then transitions to `held`, then execution for `accepted`/`held` whose time has come; (4) reminders; (5) stuck-message sweep. Message handling (commands, new instructions) runs before the sweep within a cycle. A row is therefore never executed in the same pass that finds it expired.

**Park rule (R5-T6, ONE rule).** A `Route.kind == "park"` (the record is complete: amount, source and payee data are known, e.g. `beneficiary_list_unavailable`, `beneficiary_ambiguous`, `possible_duplicate`, account-number mismatch, cap) is stored by `store.create` with `status='parked'` and `outcome_code=<reason>`: the row exists as `parked` from creation, there is no `accepted -> parked` hop, and the problem email is sent only when `created` is True (a rerun sends nothing). `create` accepts only `INITIAL_STATUSES = {accepted, awaiting_beneficiary, awaiting_confirmation, held, parked}`; creation is not a `TRANSITIONS` edge. A stop BEFORE a complete record exists (reconcile `conflict`/`none`, non-ZAR currency, source account unresolved or ambiguous) creates NO instruction row (`amount` and `source_account_id` are NOT NULL), sets the `payment_message_seen` outcome `parked_<reason>` and sends the same single problem email. The transitions to `parked` in the table above (pre-claim re-verification failures, a `daily_cap` claim refusal, `PaymentNotSent`) stay `cas_status`/`finalize` calls on an existing row. **`path` (R6-T1):** every created row, parked-at-creation included, carries `path` computed BEFORE the duplicate guard and the route (rule in 2b), so a row parked for `possible_duplicate`, an account-number mismatch or `beneficiary_list_unavailable` always satisfies the `path` CHECK.

**Notice rule (R5-T2, binding).** Every email about an instruction row goes to `record['notify_to']`, stored at create from the allowlisted `auth_from` of the creating message (never Reply-To, never an address extracted from a body or image), so it still works after `payment_message_seen` cleanup. Terminal notices (executed confirmation, failed, needs_review, needs_authorisation, expired, parked) are sent only by the caller whose `cas_status`/`finalize`/`create` returned True (the CAS winner), so no per-notice column is needed; `cancelled` sends no email (the sender just asked for it). The set-once stamps cover only the notices that are not a state change: paste, hold, reminder, confirm_request.

**`expires_at` meaning (R5-T6/2b).** `expires_at` is NOT NULL and is the expiry of the CURRENT non-terminal state: `awaiting_beneficiary` = creation `now + PAYMENTS_AWAITING_EXPIRY_DAYS`; `awaiting_confirmation` = creation `now + PAYMENTS_CONFIRM_EXPIRY_HOURS`; `held` = `execute_after + PAYMENTS_HELD_EXPIRY_HOURS` (set at creation for a directly held row, replaced by `set_held` for an awaiting row that becomes held); `accepted` = informational `received_at + PAYMENTS_MAX_MESSAGE_AGE_HOURS` (the binding freshness test is `coalesce(accepted_at, received_at)`, section above); `parked` at creation = creation `now` (terminal; never swept).

**Daily-total reservation (TF, NB-R3-5, R4-T6).** `claim_for_execution` adds the amount to `payment_daily_total` for the SAST day of the claim and, in the same transaction, sets `daily_reserved = true` and `reserved_day = <that day>` on the instruction. EVERY exit from `submitting` is ONE call, `store.finalize(instruction_id, expected='submitting', new_status, *, release: bool, now, outcome_code=None)`, a single transaction: `UPDATE payment_instruction SET status = %s, updated_at = %s, ... WHERE instruction_id = %s AND status = %s RETURNING amount, reserved_day, daily_reserved`; when `release` is true and the RETURNED `daily_reserved` is true it then sets `daily_reserved = false` and subtracts the RETURNED amount from the `payment_daily_total` row of the RETURNED `reserved_day` (`greatest(total - amount, 0)`; never the day of `now`). Status change and release commit or roll back together, so a crash cannot leave a terminal row with a live reservation or the reverse; a second call finds the status no longer `submitting`, returns False and changes nothing. `release` must match `FINALIZE_RELEASES = {executed: False, needs_review: False, failed: True, needs_authorisation: True, parked: True}`; any other combination raises `ValueError` (programming error). A claim at 23:59 SAST finalized at 00:01 therefore restores the previous day and leaves the new day untouched. Without the release a definite failure would consume the R50,000 cap for the day. `recover_stale_submitting` is a plain status UPDATE to `needs_review` and keeps the reservation.

`instructions.TRANSITIONS: dict[str, frozenset[str]]` encodes the "Leaves to" column exactly; `cas_status` and `claim_for_execution` raise `ValueError` for any `(expected, new)` pair outside it (programming error, not a runtime park), `cas_status` also refuses `new='submitting'` (use the claim) and `expected` containing `'submitting'` (use `finalize`), and `finalize` checks `('submitting', new_status)` against it. Terminal states map to `frozenset()`.

    * **One parser (R5-B1):** `cmd = commands.parse_command(view)` (S7, pure) is computed once and the branches below dispatch on `cmd` only; no other code in the cycle reads a command, and `confirm` is never inferred from `raw_first_line` or from a keyword inside longer text (`do not confirm, the amount is wrong` is `None`). `cmd == "cancel"` is accepted, with the instruction in `awaiting_*` or `held`, when the first non-empty line of the confident typed text, or fail-safe `view.raw_first_line`, is the whole word `cancel` (grammar in S7). An authenticated mail resolving to one active ref is accepted EVEN WHEN the split is not confident and EVEN WHEN the mail is older than the age window (Outlook desktop replies are unsplittable and would otherwise have the cancel dropped while the held payment executes). The loop guard never blocks it (it keys only on our own headers/sentinel). A cancel on an `accepted`/`submitting` row is a no-op audited `cancel_too_late` (Q2: not cancellable).
    * `cmd == "confirm"` (first non-empty line of the CONFIDENT typed text is the whole word `confirm`) additionally requires an authenticated sender, a row in `awaiting_confirmation` within its expiry (any other state: no-op audited `confirm_not_applicable`), and the CONFIRM mail's own freshness (B5): the age rule of 5b is evaluated here for the confirm mail (stale or missing receipt time -> ignored, audit `expired_age`, no email). On success `cas_status(awaiting_confirmation -> accepted, accepted_at=<the confirm mail's trusted receipt time>)` and `execute_instruction` runs in the same cycle (R4-T1/T3).
    * `cmd == "ambiguous"` (both words `cancel` and `confirm` anywhere in the confident typed text) -> no-op, audit `command_ambiguous`, no email, nothing changes.
    * `cmd is None` on an authenticated mail with a valid active ref (e.g. `Cancel please`, `please cancel this`, `do not confirm, the amount is wrong`) -> `build_not_understood_email` ("not understood; executes at <execute_after>; reply cancel") sent to `record['notify_to']`, RATE-LIMITED to one per instruction per 24h (`meta_get/meta_set` key `notice:not_understood:<instruction_id>`, TR3-1) and audited `command_not_understood`; nothing else happens, in particular an `awaiting_confirmation` row is never moved.
    * **Cancel not matched (NB-R3-4).** An authenticated mail with `commands.parse_command(view) == "cancel"` but which resolves NO single active ref (subject tag removed AND no usable `In-Reply-To`/`References`, or two distinct refs) NEVER auto-cancels a guess: it gets `build_cancel_not_matched_email` (rate-limited per sender per 24h via `notice:cancel_unmatched:<hash(auth_from)>`) and is audited `cancel_not_matched`, then NOT processed as a new instruction (no trigger can arise from a bare `cancel`).
    * commands are never read from quoted/forwarded/subject text beyond the raw-first-line cancel rule above.

## 4. Risks and decisions needed from the human

1. **Immediate payment has no cancel window (Q2).** A registered, established payee is paid in the same cycle. The controls are sender authentication (From allowlist plus strictly aligned dkim/spf), registered-payee-only, caps, and our own re-verification. A compromised or spoofable mailbox that passes dkim/spf can send "pay 123" and money moves within 15 minutes. Options: keep as decided; lower the caps for the soak (env-only); or hold registered payees too (routing change already supported by `registered_hold`). Recommendation: soak with low caps in G1.
2. **R20,000 community API limit vs R30,000 cap (Q7).** The community FAQ says Investec's per-payment API limit is R20,000 (unverified, not in the swagger). Payments between R20,000 and R30,000 may be rejected; the code treats that as `failed`, notifies, never retries (F40). Human to confirm with Investec or lower the cap; the G2 sandbox cannot verify it.
3. **The 24h rule is unconfirmed, and the "paid once online first" blocker.** The swagger has no 24h rule; the community FAQ says a beneficiary must have been paid once in Investec Online first. A brand-new beneficiary may still be rejected after our 24h hold and then ends `failed` with a notification. The hold is configurable (`PAYMENTS_HOLD_HOURS`, default 24). Confirm by one real small online payment to a new payee after enabling the API key.
4. **Image engine (Q10), OPEN.** Default `none` (images skipped) until chosen; adapter is S14.
   * Option A, Claude vision API (recorded default): best accuracy. Cost: egress to `api.anthropic.com` from the runner; new secret `ANTHROPIC_API_KEY`; a dependency (SDK, or plain `requests`); bank details in images leave the machine (POPIA). Mitigations are in the design: strict JSON schema, no tools, no action field, `validate_extraction`, trigger/last-3 only from typed text, Q11 policy, conflicts park.
   * Option B, local tesseract OCR: no egress, no new secret. Cost: `apt-get install tesseract-ocr` in the job (+ optional `pytesseract`), lower accuracy, more misreads (Q11 and the conflict rule catch them), added setup time per run unless cached.
   * Either way it is a swap behind `ImageExtractor`.
5. **Q11 image-amount policy, OPEN.** Default `confirm`: an image-derived amount to a registered payee does not pay immediately; the user replies "confirm" (authenticated, confident typed text). Alternatives: `hold` (standard hold, then pay unless cancelled; `execute_after = max(now, first_seen_at) + hold`) or `immediate` (not recommended). Human to choose.
6. **Pay-key split (Q9/F27).** Listing beneficiaries needs the same `beneficiarypayments` scope as paying, so either the read key gains payment power (rejected by domain advice) or the v2 cycle uses the payment key for listing in the payments job only. Plan: v2 dry-run uses the read credential; if listing fails (403) the cycle parks `beneficiary_list_unavailable` and sends no paste emails. In practice the payments job probably needs the payment key even in dry-run. Human to decide whether to put the payment-scoped key in the Actions payments job from G1 (read-only use while live is off).
7. **Live stays OFF; gates G1-G3.** Nothing in this run turns live on. G1: 14-day dry-run soak (at least 5 real instructions, audit reviewed). G2: sandbox end-to-end incl. error bodies and no-retry. G3: the human sets `PAYMENTS_LIVE_ENABLE` as a repo variable, adds `INVESTEC_WRITE_*` secrets and caps; never the loop.
8. **IMAP crash window.** `ImapInbox` fetches `RFC822` without PEEK and marks mail seen before processing. A crash after fetch drops the instruction (fails safe). v2 mitigates by writing `payment_message_seen` first and sweeping stuck rows into a "please resend" notice to authenticated senders only (TF); the fetch change itself stays out of the safe set (no test seam, `pragma: no cover`). Human may want a follow-up run.
