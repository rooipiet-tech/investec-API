```python
    # returns (authserv_id, [(method, {"result", "header.d", "header.i", "header.from", "smtp.mailfrom"}), ...]);
    # malformed -> AuthParseError -> caller treats as no_trusted_auth_results
def trusted_auth_results(headers: Sequence[str], trusted_authserv_ids: frozenset[str]) -> list[tuple[str, dict[str, str]]] | None

    # None unless its authserv-id equals a configured id exactly (case-insensitive); lower headers are never read

    # feature-detects the `strict` keyword of email.utils.getaddresses (added by a CPython security patch release,
    # not present on early 3.12 patch releases; confirm the exact patch number at build time and record it in the runbook)

```
Rules (all must hold; any failure -> `ok=False`, reason code only):
1. `from_headers` (from `msg.get_all("From")`) has EXACTLY one element and `email.utils.getaddresses([h], strict=True)` yields exactly one address; address and `From` header are pure ASCII (non-ASCII / IDN / lookalike -> `non_ascii_from`); the address is in `allowlist` exactly (no dot/plus equivalence). If `strict_address_parser_available()` is False the function FAILS CLOSED with `strict_parser_unavailable` (it never falls back to a lax parser); the cycle preflight (S11) surfaces this as an error envelope so it is loud, not silent.
2. Topmost `Authentication-Results` only; its authserv-id must equal a configured id (`PAYMENTS_AUTHSERV_ID`, default `mx.google.com`; `PAYMENTS_AUTHSERV_IDS` kept as a comma alias, only the topmost header's id is matched against the set).
3. `dkim=pass` where the DKIM domain comes from `header.d` OR `header.i` (for `header.i` the part after the last `@`, or the bare value if no `@`; Gmail reports `header.i`); `spf=pass` with the `smtp.mailfrom` domain.
4. STRICT alignment: the dkim domain and the `smtp.mailfrom` domain each equal the From domain exactly (no parent-organisation relaxation). Any `fail`/`softfail`/`none`/`temperror`/`permerror` for dkim or spf rejects. Multiple dkim results: all must pass and at least one aligned.
5. **DMARC (TD).** A `dmarc=fail` (or `temperror`/`permerror`) result REJECTS (`dmarc_fail`). When a `dmarc=pass` result is present its `header.from` must equal the From domain, else `dmarc_header_from_mismatch`. An absent or `dmarc=none` result is ACCEPTABLE, because dkim AND spf are already required to pass strictly aligned with the parsed From; this is APPROVED by the human (Amendment 3 item 14, F47) and tested both ways.

**`payments/commands.py` (new, pure, stdlib; built in S7 right after `content.py`, so it exists before S10 and S11).** The ONE command parser for the batch-approval grammar (F14); S10's template test and S11 step 4 call it and nothing else reads a command. It replaces the former `cancel`/`confirm` grammar (the per-item confirm path no longer exists).
```python
@dataclass(frozen=True)
class Command:
    kind: str                  # "approve_all" | "approve" | "cancel" | "invalid"
    numbers: tuple[int, ...]   # () for approve_all and invalid; ascending, unique, each 0..999 as typed for approve/cancel
    reason: str                # "" unless kind == "invalid": "bad_syntax" | "duplicate_number" | "bare_cancel" | "both_verbs_in_text"
def parse_command(view: TextView) -> Command | None      # None = not a command at all
```
Grammar (binding; a builder must not read "approve" as "the word approve anywhere"; item numbers extend the same safety properties as the earlier cancel/confirm grammar, NB3, NB-R3-4, R5-B1):
* **Source.** ONLY `first_line(view.typed_text)` = the first line whose `strip()` is non-empty, and ONLY when `view.confident`. When `confident` is False `typed_text` is `""`, so no command is possible. There is NO fallback to `raw_head_lines` for any verb (the former raw-first-line cancel rule is removed: nothing executes without approval, so a cancel that is missed merely lets the item expire, and an approval that is missed merely leaves it pending; a fail-open rule has no remaining purpose). Quoted, forwarded, subject, attachment and image text are never inspected (images never carry commands, F14).
* **Normalisation.** The line must be pure ASCII (`str.isascii()`, so look-alike letters never match; a non-ASCII line is `None`); `casefold()`; leading/trailing whitespace stripped; ONE run of trailing punctuation from the set `. ! , ;` removed.
* **Accepted shapes** (full match on the normalised line): `approve` -> `approve_all`; `approve N` / `approve N M ...` / `approve N, M` -> `approve`; `cancel N` / `cancel N M ...` / `cancel N, M` -> `cancel`. `N` is `0` or a number of 1-3 digits without a leading zero. Separators between numbers are whitespace (spaces/tabs) or a comma with optional spaces; nothing else (no ranges such as `1-3`, no `and`, no `&`, no `all`, no `#`).
* **Invalid (a recognised verb with a malformed or contradictory line, always a no-op the caller reports):** the line starts with the whole word `approve` or `cancel` but does not match an accepted shape (`approve x`, `approve cancel`, `approve 1 cancel 2`, `approve please`, `cancel please`, `approve 1-3`, `approve 01`) -> `invalid/bad_syntax`; a repeated number (`approve 1 1`) -> `invalid/duplicate_number`; bare `cancel` -> `invalid/bare_cancel` (cancel needs numbers, confirmation C1); the first line is an accepted approve/cancel shape but the REST of the confident typed text contains the OTHER verb as a whole word (`approve\ncancel 2`) -> `invalid/both_verbs_in_text` (the earlier "both words anywhere" safety property, extended).
* **None:** every other first line (`thanks`, `please approve`, `do not approve`, `I approve`, an empty typed text, `approve` only on line 2).
* **Range is NOT the parser's job** (it does not know the batch): S11 checks every number against the batch's item numbers; any number outside the batch (`approve 0`, `approve 9` on a 3-item batch) makes the WHOLE command a no-op with the not-understood notice (all-or-nothing, nothing partially applied).
* Examples: `approve` -> approve_all; `Approve.` -> approve_all; `approve 1 3` -> approve (1, 3); `Approve 2` -> approve (2,); `cancel 2` -> cancel (2,); `cancel 2, 3!` -> cancel (2, 3); `approve 0` -> approve (0,) (rejected later as out of range); `approve 9` -> approve (9,) (rejected later when the batch has fewer than 9 items); `cancel` -> invalid/bare_cancel; `approve x` -> invalid/bad_syntax; `approve 1 1` -> invalid/duplicate_number; `please approve` -> None; `do not approve, the amount is wrong` -> None; `thanks\napprove` -> None; `approve\ncancel 2` -> invalid/both_verbs_in_text.

## 2a. State and transition table - the single source for the 0013 CHECK list, `TRANSITIONS`, and S11

This table is frozen BEFORE S9; S9's SQL, `instructions.TRANSITIONS`, both stores and S11 are derived from it. There is ONE approval path (Amendment 3): `new -> awaiting_approval -> accepted -> submitting -> executed | failed | needs_review | needs_authorisation`; nothing is created in, or can enter, `accepted` except through `InstructionStore.approve_item` (an authenticated approval reply, F14), so no code path can reach the write endpoint for an unapproved item (F12, F45). Time bases: "message fresh" means `now - received_at <= PAYMENTS_MAX_MESSAGE_AGE_HOURS` (default 24), applied to a NEW instruction message (S11 5b) and to an APPROVE reply (not to a cancel). `received_at` is the trusted receipt time: the IMAP `INTERNALDATE` and the topmost `Received` header timestamp are both read, and when both exist the OLDER of the two is used (stricter), when only one exists that one is used, when neither exists the message fails closed (`expired_age`); the `Date` header is never used. Item windows: an `awaiting_approval` item expires `PAYMENTS_APPROVAL_EXPIRY_HOURS` (default 24, F16) after it was OFFERED in a batch (`offered_at`); an `accepted` item expires `PAYMENTS_APPROVED_GRACE_HOURS` (default 24, F16) after `approved_at`; `awaiting_beneficiary` keeps `PAYMENTS_AWAITING_EXPIRY_DAYS` (default 7); `held` expires `PAYMENTS_HELD_EXPIRY_HOURS` (default 24) after `eligible_at`. All four parse like the age window: unparsable or <= 0 -> 0 = already expired (fail closed).

**Sweep order (per cycle, per row, binding).** (1) `recover_stale_submitting`; (1b) BEFORE any message is handled, `snapshot = {instruction_id of every row in status accepted}` is captured (this is what makes "approved items execute in the NEXT cycle" structural: a row approved during this cycle's message handling is not in the snapshot, so it cannot execute in this cycle, F45); (2) for every non-terminal row the EXPIRY check comes FIRST (`expires_at <= now`): an expired row becomes `expired` and nothing else is evaluated for it; (3) `awaiting_beneficiary` rows whose beneficiary is now listed -> `held`; `held` rows with `eligible_at <= now` -> `awaiting_approval` (with hold 0 both happen in the same pass); (4) execution of the rows in the snapshot that are still `accepted`; (5) the BATCH OFFER step (S11): ready items are numbered, a batch ref is assigned and ONE batch email goes out (F43); (6) notice sweep and stuck-message sweep. Message handling (approval replies, new instructions) runs before steps (1)-(6) within a cycle. A row is therefore never executed in the pass that finds it expired, and never in the cycle that approved it.

**Approval semantics (binding, F14/F16/F43/F44/F45).**
* A batch is identified by exactly ONE batch ref found in the reply's Subject/In-Reply-To/References (`refs.find_batch_ref`), and applies ONLY to rows with that `batch_ref` AND `notify_to` equal to the replying authenticated address AND status `awaiting_approval` (approve) or `awaiting_approval`/`accepted` (cancel) AND not expired. Zero refs, two distinct refs, an unknown ref, a ref owned by another approver, or an item number outside the batch -> NO-OP, nothing changes, the sender gets the batch-not-matched or not-understood notice.
* `approve` (all) / `approve N M`: for each target item `approve_item` runs one CAS (`awaiting_approval -> accepted` guarded by `status`, `batch_ref`, `item_no`, `expires_at > now`, sets `approved_at = now`, `expires_at = now + grace`); an item that is not `awaiting_approval` (already approved, executed, cancelled, expired, parked) is SKIPPED with a reason code in the acknowledgement; the call is idempotent per item, so the same approval processed twice (the same mail again, or two replies) approves nothing twice and never executes twice. An approve reply must itself be fresh (message age window) and must not predate the batch (`reply_received_at >= offered_at`); a cancel is never age-gated (safe direction).
* `cancel N M`: `cas_status(expected={awaiting_approval, accepted} -> cancelled)` per item; items past `submitting` (or terminal) are skipped ("too late", F14: a re-approve/re-cancel of an executed item is a no-op).
* Unmentioned items stay pending until expiry and are re-listed in the next batch email (F43).
* An approval does not waive any check: F15 re-verification runs immediately before the POST for every approved item (beneficiary registered and fingerprint unchanged, source unique, balance, per-payment and daily caps, `offer_digest` equals the digest of the stored row, approval still valid), and a mismatch parks the item and notifies (the payee, amount or source "changed since the batch was sent").

**Park rule (R5-T6, ONE rule).** A `Route.kind == "park"` (the record is complete: amount, source and payee data are known, e.g. `beneficiary_list_unavailable`, `beneficiary_ambiguous`, `possible_duplicate`, account-number mismatch, over the per-payment cap) is stored by `store.create` with `status='parked'` and `outcome_code=<reason>`: the row exists as `parked` from creation, and the problem email is sent only when `created` is True (a rerun sends nothing). `create` accepts only `INITIAL_STATUSES = {awaiting_approval, awaiting_beneficiary, held, parked}` (never `accepted`); creation is not a `TRANSITIONS` edge. A stop BEFORE a complete record exists (reconcile `conflict`/`none`, non-ZAR currency, source account unresolved or ambiguous) creates NO instruction row (`amount` and `source_account_id` are NOT NULL), sets the `payment_message_seen` outcome `parked_<reason>` and sends the same single problem email. The transitions to `parked` in the table above stay `cas_status`/`finalize` calls on an existing row. **`path` (R6-T1):** every created row, parked-at-creation included, carries `path` computed BEFORE the duplicate guard and the route (rule in 2b), so a parked row always satisfies the `path` CHECK.

**Notice rule (R5-T2, binding).** Every email about an instruction row goes to `record['notify_to']`, stored at create from the allowlisted `auth_from` of the creating message (never Reply-To, never an address extracted from a body or image), so it still works after `payment_message_seen` cleanup; a batch contains only rows of one `notify_to` and goes to that address. Terminal notices (outcome of an executed item, failed, needs_review, needs_authorisation, parked, and the grouped expiry notice) are sent only by the caller whose `cas_status`/`finalize`/`create` returned True (the CAS winner), so no per-notice column is needed. The set-once stamps cover the notices that are not a state change: paste (`paste_notified_at`), beneficiary-first-observed (`hold_notified_at`) and the batch email (`batch_notified_at`, per batch). Approval-path emails (command acknowledgement, not-understood, batch-not-matched) are sent once per processed message: the `payment_message_seen` identity row makes a rerun skip the message, so no rate-limit stamp is needed (the former meta rate limits are removed; the loop guard keeps our own notices from being processed).

**`expires_at` meaning (R5-T6/2b).** `expires_at` is NOT NULL and is the expiry of the CURRENT non-terminal state: `awaiting_beneficiary` = creation `now + PAYMENTS_AWAITING_EXPIRY_DAYS`; `held` = `eligible_at + PAYMENTS_HELD_EXPIRY_HOURS` (set at creation for a directly held row, replaced by `set_held` for an awaiting row that becomes held); `awaiting_approval` = provisional `now + approval window` at creation or at `make_ready`, REPLACED by `offered_at + approval window` when the batch offers it; `accepted` = `approved_at + PAYMENTS_APPROVED_GRACE_HOURS`; `parked` at creation = creation `now` (terminal; never swept).

**Daily-total reservation (TF, NB-R3-5, R4-T6).** `claim_for_execution` adds the amount to `payment_daily_total` for the SAST day of the claim and, in the same transaction, sets `daily_reserved = true` and `reserved_day = <that day>` on the instruction. EVERY exit from `submitting` is ONE call, `store.finalize(instruction_id, expected='submitting', new_status, *, release: bool, now, outcome_code=None, outcome_message=None)`, a single transaction: `UPDATE payment_instruction SET status = %s, updated_at = %s, ... WHERE instruction_id = %s AND status = %s RETURNING amount, reserved_day, daily_reserved`; when `release` is true and the RETURNED `daily_reserved` is true it then sets `daily_reserved = false` and subtracts the RETURNED amount from the `payment_daily_total` row of the RETURNED `reserved_day` (`greatest(total - amount, 0)`; never the day of `now`). Status change and release commit or roll back together; a second call finds the status no longer `submitting`, returns False and changes nothing. `release` must match `FINALIZE_RELEASES = {executed: False, needs_review: False, failed: True, needs_authorisation: True, parked: True}`; any other combination raises `ValueError` (programming error). A claim at 23:59 SAST finalized at 00:01 restores the previous day and leaves the new day untouched. `recover_stale_submitting` is a plain status UPDATE to `needs_review` and keeps the reservation. Large batches: nothing is reserved at approval time, only at claim time, so a batch whose total exceeds the daily cap executes in `approved_at, batch_ref, item_no` order until a claim is refused with `daily_cap`; each refused item is parked (terminal, notified), never retried the next day (R6-T2, risk R32).

A `submitting` row found at cycle start follows `recover_stale_submitting(older_than=...)` only. Stored values only, never re-parsed mail.

`payments/approval.py` (the approval/cancel handler, called by cycle step 4)
```python
def handle_approval_message(settings, store, audit, *, auth_from: str, batch_refs: Sequence[str], cmd: Command | None,
                            received_at: datetime | None, now: datetime, smtp_send) -> str   # returns the message outcome code
```
Behaviour (2a "Approval semantics" is the contract): not exactly one batch ref, or no rows for `store.list_batch(ref, auth_from)` -> `build_batch_not_matched_email`, outcome `approval_noop`; `cmd is None` or `cmd.kind == "invalid"` -> `build_not_understood_email` (reason code), nothing changes; any number outside the batch's item numbers (`approve 0`, `approve 9`) -> the whole command is a no-op with the not-understood notice listing the valid numbers; `approve_all`/`approve`: the reply must have a trusted `received_at` that is fresh (message age window, else audit `expired_age`, no email) and `>= offered_at` (else audit `approval_predates_batch`, no email), then per target item `store.approve_item(...)` (an item that is not `awaiting_approval` is skipped with a reason, an expired item is skipped as `expired`); `cancel`: per target item `store.cas_status(expected={awaiting_approval, accepted} -> cancelled)` (never age-gated); ONE `build_command_ack_email` per processed message (approved / cancelled / skipped with reasons); audit steps `approve`, `cancel`, `approval_noop` carry the batch ref (key `ref`) and counts only. The handler never calls `execute_instruction`: approval only moves rows to `accepted`; execution happens in a later cycle (F45).

`payments/batch.py` (the batch offer step, called by cycle step 5)
```python
def offer_batches(settings, store, audit, *, beneficiaries, raw_beneficiaries, now: datetime, smtp_send,
                  new_ref: Callable[[], str]) -> dict    # summary: batches_sent, items_offered, pre_offer_parked, deferred
```
For every `notify_to` that has UNOFFERED `awaiting_approval` rows: (1) when `beneficiaries is None` (list fetch failed) offering is DEFERRED for the whole cycle (audit `offer_deferred_list_unavailable`; the rows stay unoffered, their provisional expiry still applies); (2) each unoffered row is re-verified with `execute.reverify_beneficiary` (and the fingerprint key must be present); a failure -> `cas_status(awaiting_approval -> parked, <reason>)` + problem email only if that CAS wins, never offered; (3) `rows = store.offer_batch(notify_to, now=now, approval_window=..., max_items=PAYMENTS_MAX_BATCH_ITEMS, new_ref=new_ref)`: ONE transaction numbers 1..n and assigns the ref; empty -> NO email (F43: no empty batches, no email on a cycle with nothing new); (4) `pending = store.list_pending_offered(notify_to, now=now, exclude_batch_ref=ref)` (the "still pending" section, never re-offered, never duplicated); (5) `build_batch_approval_email` -> `smtp_send`; on success `mark_batch_notified(ref)`; if the send raises, `unoffer_batch(ref)` (rows return to unoffered and are offered under a NEW ref next cycle), audit `batch_send_failed` (class name only), the cycle continues. Payee names in the lines come from the fresh beneficiary list by `beneficiary_id`, else `payee_name_norm`. Exactly ONE batch email per `notify_to` per cycle (one in total with a single allowlisted sender). The notice sweep (cycle step 6) re-sends the batch email for any batch whose `batch_notified_at` is still null after `PAYMENTS_STUCK_MESSAGE_MINUTES` (the crash window between `offer_batch` and the send), then `mark_batch_notified`; at worst a duplicate copy of the SAME batch (same ref, same numbers, no state change) goes out.

`payments/cycle.py`
```python
def run_instruction_cycle(settings, *, inbox, client, store, audit, smtp_send=None,
                          extractor=None, now: Callable[[], datetime] | None = None,
                          allow_non_durable: bool = False) -> dict      # allow_non_durable is for tests; the CLI never passes it
    # smtp_send: Callable[[EmailMessage], None]; when None the cycle uses functools.partial(emailer._smtp_send, settings) (R4-T11b: the existing, unmodified
    # emailer module; payments.notify is a legacy file and is not used); every email goes through it, never anything else
    # extractor: when None -> images.get_extractor(settings) (Null unless ANTHROPIC_API_KEY and IMAGE_EXTRACTOR_MODEL are both set)
```
**Preflight, in this order, ALL before any IMAP fetch (fetch marks mail read).** Each failure returns the v2 error envelope (rc 2; the envelope prints the exception class name + `v2_cli.scrub_message(text, settings)`, T15, R4-T5) and fetches NO mail:
1. **`v2_requires_durable_store` (NB4).** `PAYMENTS_MODE=v2` with `PAYMENTS_STATE_BACKEND` other than `postgres` (the default is `file`) is refused; `not store.durable and not allow_non_durable` is refused too. Otherwise each 15-minute process would start with an empty daily total, message-seen table, duplicate guard and batch state, so the R50,000 cap would reset every run and pending approvals would be lost. `MemoryInstructionStore` is only ever injected by tests. `cli.py` builds `PgInstructionStore` only for the postgres backend.
2. `mailbox_not_dedicated`: `IMAP_MAILBOX` empty or `INBOX` (case-insensitive) (T3).
3. `strict_parser_unavailable` if `sender_auth.strict_address_parser_available()` is False (TD, F48): nothing processed, error envelope, error audited, write not called.
4. `store.ping()` (selects from the four 0013 tables): unreachable -> error; tables missing -> `store_not_initialised` (`init-db` must have run).

Then per cycle: (a) audit `cycle_start`; (b) `recover_stale_submitting`; **(b0) snapshot (2a step 1b): `snapshot = {r["instruction_id"] for r in store.list_by_status({"accepted"})}`, captured BEFORE any message is handled**; (c) fetch beneficiaries ONCE (raw list for fingerprints and the parsed `Beneficiary` list); on exception set `beneficiaries=None` (NOT an empty list: a failed fetch must never look like "new payee" and spam paste emails) -> new instructions park `beneficiary_list_unavailable`, existing awaiting/held rows untouched, batch offering deferred; (d) T12 bootstrap if `not store.bootstrap_done()` AND the list was fetched (even if empty): `observe_beneficiary(..., established=True)` for every listed id then `mark_bootstrap_done`; otherwise `observe_beneficiary(...)` for every listed id (updates `last_fingerprint`/`fingerprint_changed_at`; null -> value is a baseline, TR3-13b); (e) fetch messages; **(e') identity PRE-PASS (TR3-3):** for ALL fetched messages compute the instruction id (`refs.instruction_id_for`) and `mark_message_seen` (`processing` row) BEFORE any message is processed (IMAP has already marked them read, so a crash or an exception in message 1 must not lose messages 2..n; the stuck sweep reports any row left `processing`); (f) per message, each wrapped in its OWN try/except (an exception sets outcome `error`, is audited by class name, and the loop CONTINUES with the next message; a cancel later in the batch is still honoured), in this order:
 1. **Identity (B4):** missing Message-ID -> reject (`no_message_id`); the row was inserted in (e'); a row that was already seen before this cycle (`mark_message_seen` returned False in (e')) -> skip entirely. This is also what makes the same approval reply, processed twice, a no-op (per-item idempotency additionally holds through the `approve_item` CAS when two DIFFERENT mails both say `approve`).
 2. **Parse once, text view, loop guard (NB1/B8/TR3-1, R4-B2), before auth:** `msg = email.message_from_bytes(v2.raw)`; `view = content.text_view(msg)` (text/html parts only: no attachment, image or `message/rfc822` access, so it is safe on unauthenticated mail); `loopguard.is_own_notification(message_id, auto_submitted, x_header, view.raw_head_lines, subject)` -> audit `own_notification` (reason code), outcome set, no reply, no state. Uses the message's own Message-ID/headers and the content sentinel (`own_body`, any of the first 3 non-empty lines, subject without a reply prefix) ONLY, never References/In-Reply-To.
 3. **`authenticate_sender`** on the OUTER From + `auth_results` (F6/F47/F48; fail -> audit `auth_failed` reason code, ignored, no state, no reply to the sender, so an unauthenticated "approve" with a valid batch ref approves nothing and gets no answer). On ok: `set_message_outcome(..., auth_from=<address>)`.
 4. **Approval path (F14/F44), before the new-instruction path and independent of any age gate for cancel.** `batch_refs = refs.find_batch_refs(subject, in_reply_to, references)` (Subject tag or the batch ref embedded in OUR OWN Message-ID echoed in `In-Reply-To`/`References`, never the body) and `cmd = commands.parse_command(view)` (S7, pure; computed ONCE; no other code in the cycle reads a command; a command is never inferred from `raw_head_lines`, quoted, forwarded, subject or image text). The message is consumed by this path (and never becomes a new instruction) when `batch_refs` is non-empty, or when `batch_refs` is empty and `cmd is not None` (an `approve`/`cancel` typed with no linkage gets the batch-not-matched notice and is never guessed onto a batch). A message with no batch ref and `cmd is None` goes to step 5 (so `pay 123 ...` as a fresh email still works, and a reply to a batch email that carries a typed instruction is NOT accepted as a new instruction: new instructions must be fresh emails). Then `approval.handle_approval_message(...)` (see above) applies the command; the message outcome is `approval_applied` or `approval_noop`.
 5. **New-instruction path** (reached when step 4 did not consume the message):
    * 5a `parse_trigger(view.typed_text)` (none -> audit `ignored`, silently; malformed/ambiguous -> audited, ignored).
    * 5b **Age gate (TF, R4-T4), AFTER auth AND trigger ok**, so expiry mails go only to authenticated senders who actually asked for a payment: `received_at` per section 2a; stale or missing -> `expired_age`, one problem email to the authenticated sender, never pays. An old mail with no trigger is ignored without any email.
    * 5c `resolve_source_unique`.
    * 5d only now `content.gather_payloads(msg, view)` (attachments/images; the extractor and `extract_attachment` run only after auth ok AND trigger ok AND age ok, T16/R4-B2); candidates: typed/forwarded/quoted TEXT via `marked_amount_candidates(strip_trigger(...))` (NB5/B2), attachments via `extract_attachment`, images via extractor + `validate_extraction` (an image never supplies the trigger, the source last-3 or a command, F33); `reconcile` (sets `image_derived` and `figures_source`; ANY conflict including an image figure -> park, F35).
    * 5e FIRST compute `path` (R6-T1: `'registered'` iff `resolve_beneficiary_strict(payee, beneficiaries)` is `ok`; `none`, `ambiguous` and `beneficiaries is None` give `'new_payee'`; carried by EVERY `store.create` record, parked ones included), THEN the duplicate guard (T11/TB): `find_recent_similar(source, payee_norm, amount, now - duplicate_window)` -> `parked possible_duplicate` (an item still awaiting approval counts, so a resend of a pending instruction is not batched twice); account HMAC check (T6); `route`; `ready` -> create row `awaiting_approval` (UNOFFERED; no email now: it is numbered and mailed by this cycle's batch step, F43; `expires_at` provisional); `held` (T12, hold > 0 only) -> create `held` with `first_seen_at`/`eligible_at`; `new_payee` -> `awaiting_beneficiary` + paste email + `mark_notified('paste')` (F10, nothing batched while unregistered); `park` (R5-T6, the one rule of section 2a) -> `store.create` with `status='parked'` and `outcome_code=<reason>`, problem email only when `created` is True; a stop before a complete record exists (reconcile conflict/none, non-ZAR, source unresolved/ambiguous) creates no row, sets the message outcome `parked_<reason>` and sends the same single problem email. EVERY `store.create` record carries `notify_to = auth_from` (R5-T2), asserted to be in the allowlist before the call, `figures_source`, and the per-state `expires_at` of section 2a.
 (g) **Sweep** per section 2a order (every email about an instruction row goes to `record['notify_to']`, never to a `payment_message_seen` address that cleanup may already have removed (R5-T2); only the stuck-message `resend` uses the message row's `auth_from`): (2) EXPIRY FIRST: every non-terminal, non-`submitting` row with `expires_at <= now` -> `cas_status(... -> expired)`; the CAS winners of one cycle are grouped into ONE `build_expiry_email` per `notify_to`; (3) awaiting rows where the beneficiary is now listed -> strict resolution (`ok` -> `set_held` with `first_seen` from the observation, `eligible_at = first_seen + hold` and `expires_at = eligible_at + PAYMENTS_HELD_EXPIRY_HOURS`, plus T6 HMAC check, then `build_beneficiary_observed_email` once with `mark_notified('hold')`; `ambiguous` -> `parked beneficiary_ambiguous` + notice, never held); every `held` row with `eligible_at <= now` -> `reverify_beneficiary` then `make_ready` (hold 0: the same pass; a non-zero hold: only at `first_seen_at + hold`, F39); (4) EXECUTION: for each id in the (b0) snapshot, in `approved_at, batch_ref, item_no` order, whose row is still `accepted` -> `execute_instruction` (a row approved in THIS cycle is not in the snapshot and waits for the next cycle, F45); (5) `batch.offer_batches(...)`; (6) notice sweep and stuck-message sweep: **optional notice sweep (R6-T7):** a non-terminal row whose state has a set-once notice (`awaiting_beneficiary` -> paste, `held` -> hold) with that stamp still NULL and `updated_at` older than `PAYMENTS_STUCK_MESSAGE_MINUTES` (reused, no new setting) gets the notice sent to `notify_to`, then `mark_notified`; plus the unnotified-batch resend above; stuck-message sweep -> `resend` emails to `auth_from` only. Terminal notices are not swept (CAS-winner-only; a crash between the CAS and the send loses that notice, accepted residual, the audit shows the state). Test if built: `test_sweep_sends_missing_set_once_notice_after_crash_then_marks_once`; (h) `store.cleanup`; (i) return a JSON-able summary dict (`mode`, counts incl. `offered`, `batches_sent`, `approved`, `cancelled`, `executed`, `expired`, `parked`, per-result codes, `live_enabled`).

Any unexpected failure in the cycle body AFTER the fetch (outside the per-message try/except of (f)) sends the owner (`payments_notify_recipients`, else the allowlisted senders) a generic `build_problem_email(kind="cycle_failed")` notice with no detail (TR3-13a) and re-raises as the error envelope (T4/T15).

**New-beneficiary hold and recent registered beneficiaries (F39, T12).** The hold is `PAYMENTS_HOLD_HOURS`, DEFAULT 0 (unset/empty = 0; a value that is set but unparsable, negative or non-finite falls back to 24 as the safe direction, with an audit note, C5). `eligible_at = first_seen_at + hold`, where `first_seen_at` is OUR first observation of the beneficiary in the live list (set once, never reset, F39). With the default 0 an unregistered payee that appears in the list is `held` for at most one pass and joins the next batch at once (never before it appears); with N hours it is not batched before `first_seen_at + N h`. A registered match is routed to `held` (instead of straight to `awaiting_approval`) only when the hold is NON-ZERO and `PAYMENTS_HOLD_REGISTERED_RECENT=true` (default; inert at hold 0) and its observation is recent: `recent = (not established and first_seen_at > now - hold) or (fingerprint_changed_at is not None and fingerprint_changed_at > now - hold)`; `recent_anchor = max(first_seen_at if not established else None, fingerprint_changed_at)`; `eligible_at = recent_anchor + hold`; `recent_beneficiary = true`. A fingerprint change does NOT reset `first_seen_at`. First-deploy bootstrap (marker, S9) makes the beneficiaries present at enablement `established`. A hold never replaces approval: after the hold the item still waits for the batch approval (F12), and Investec may still reject a brand-new beneficiary (F40, F41: `failed` with Investec's message, notified, never resent).

1. **C1 Bare `cancel`.** Not a command; `cancel` needs item numbers (`cancel 2`). A bare `cancel` gets the not-understood notice and changes nothing. If the human wants "cancel with no numbers = cancel the whole batch" it is a one-line parser change (S7) with the matching test inverted.
2. **C2 First line only, ref from headers only.** Commands are read from the first non-empty line of CONFIDENT typed text; the batch is found from Subject/In-Reply-To/References, never from a ref typed in the body.
3. **C3 One batch email per approver per cycle.** With one allowlisted sender (the intended deployment) that is exactly one email per cycle; with several senders each gets their own batch and can approve only items created from their own mails.
4. **C4 Quote-stripped mobile replies.** Because every approval is a reply, a mail client that strips the quote leaves no boundary, `confident` is False, nothing is approved and the sender gets a not-understood notice. The runbook and the batch email say: reply with only the command on the first line above the quote. If this proves annoying in the G1 soak, the human may accept a relaxation (for example: a reply whose In-Reply-To is OUR batch Message-ID and whose whole body is a single short command line counts as confident); that relaxation is NOT in this plan because the human's instruction is "first non-empty line of CONFIDENT typed text only".
5. **C5 Hold setting parsing.** `PAYMENTS_HOLD_HOURS` unset/empty = 0 (the F39 default); a set-but-unparsable, negative or non-finite value falls back to 24 hours (the safe direction) with an audit note.
6. **C6 Per-payment cap before offer.** An item over the per-payment cap is parked (notified) and never offered, so the user is not asked to approve something that cannot run; both caps are still re-checked at execution (F15, F18).
7. **C7 Pay-key split (Q9/F27).** Listing beneficiaries needs the same `beneficiarypayments` scope as paying, so either the read key gains payment power (rejected by domain advice) or the v2 cycle uses the payment key for listing in the payments job only. Plan: v2 dry-run uses the read credential; if listing fails (403) the cycle parks `beneficiary_list_unavailable`, defers batch offering and sends no paste emails. In practice the payments job probably needs the payment key even in dry-run. Human to decide whether to put the payment-scoped key in the Actions payments job from G1 (read-only use while live is off).
8. **C8 Investec rejection body shape.** The field that carries Investec's rejection message (`ErrorMessage`, `message`, `error_description`, `error`) is unverified; the sanitiser keeps whatever is found and the G2 sandbox run must confirm the shape. A rejected payment is always `failed`, notified and never resent.
9. **C9 R20,000 community limit vs R30,000 cap (Q7).** The community FAQ says Investec's per-payment API limit is R20,000 (unverified, not in the swagger). Payments between R20,000 and R30,000 may be rejected; the code treats that as `failed`, notifies, never retries (F40). Human to confirm with Investec or lower the cap; the G2 sandbox cannot verify it.

Standing notes (not decisions):
* **24h rule and "paid once online first" (F41).** The swagger has no 24h rule; the hold is an app-side setting (default 0h). The community FAQ says a beneficiary must be paid once in Investec Online first; a brand-new beneficiary may be rejected even at hold 0 and then ends `failed` with Investec's message. Confirm by one real small online payment to a new payee after enabling the API key.
* **Image reading (Q10, resolved).** Claude vision over plain `requests`; the model id is the `IMAGE_EXTRACTOR_MODEL` variable (no default, so extraction is off until set); `ANTHROPIC_API_KEY` is an Actions secret; the only new egress host is the Anthropic API; bank details in images leave the machine (POPIA, documented). Mitigations are structural: strict schema, no action field, `validate_extraction`, trigger/last-3/commands only from typed text, image-derived figures are batched and approved like everything else, conflicts park.
* **Live stays OFF; gates G1-G3.** Nothing in this run turns live on. G1: 14-day dry-run soak (at least 5 real instructions, audit reviewed). G2: sandbox end-to-end incl. error bodies and no-retry. G3: the human sets `PAYMENTS_LIVE_ENABLE` as a repo variable, adds `INVESTEC_WRITE_*` secrets and caps; never the loop.
* **IMAP crash window.** `ImapInbox` fetches `RFC822` without PEEK and marks mail seen before processing. A crash after fetch drops the instruction or the approval reply (fails safe: an unprocessed approval means the item expires, an unprocessed instruction is never paid). v2 mitigates by writing `payment_message_seen` first and sweeping stuck rows into a "please resend" notice to authenticated senders only (TF); the fetch change itself stays out of the safe set.
* **"Payment notification" field (Q6).** Rendered `(not provided)` unless the typed text has `notification:`/`notify:`.
* **Legacy token flow: RETIRED (decided, F42).** Not fixed, not scheduled, deprecated in the docs; the code stays byte-identical (S1 pins) and remains reachable only by an operator running `approve-payments` with `PAYMENTS_MODE` unset or `legacy`.
* **Plan-review gate conflict.** The standing "LOW-risk only" rule cannot hold for this feature run; S3, S5, S7, S9, S14 are MEDIUM and S11 is HIGH but contained. The orchestrator should accept them under the frozen spec or bounce specific stages.
* **Time zone.** v2 daily totals, batch-ref dates and "today" use Africa/Johannesburg; legacy store day boundaries are unchanged.
