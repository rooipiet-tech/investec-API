## (a) Pay an existing beneficiary from a chosen account – SUPPORTED
Documented (S1): `POST /za/pb/v1/accounts/{accountId}/paymultiple`, OAuth scope `beneficiarypayments`. Headers: Authorization Bearer, Content-Type application/json (x-api-key per auth section). Max 50 payments per request.
Body (additionalProperties=false): `{"paymentList":[{beneficiaryId, amount, myReference, theirReference, [authoriserAId, authoriserBId, authPeriodId, fasterPayment]}]}`. Required per item: beneficiaryId, amount, myReference, theirReference (all strings; amount is a rand string e.g. "10.12"). Optional authoriser*/authPeriodId/fasterPayment: only for payments needing authorisation; fasterPayment may be true only if beneficiary has `fasterPaymentAllowed` (from GET beneficiaries).
Response 200: `data.TransferResponses[]` {PaymentReferenceNumber, PaymentDate (dd/mm/yyyy), Status (text e.g. "No authorisation necessary / Payment effective date ..."), BeneficiaryName, BeneficiaryAccountId, AuthorisationRequired(bool)}, `data.ErrorMessage` (null when ok), plus links/meta. Errors: 400/401/403/429/500 (no bodies documented).
Account selection: accountId from `GET /za/pb/v1/accounts` (scope `accounts`) -> data.accounts[]{accountId, accountNumber, accountName, referenceName, productName, kycCompliant, profileId, profileName}. Source account = path param.
Beneficiaries: `GET /za/pb/v1/accounts/beneficiaries` (scope `beneficiarypayments`) -> data[]{beneficiaryId, accountNumber, code, bank, beneficiaryName, lastPaymentAmount, lastPaymentDate, cellNo, emailAddress, name, referenceAccountNumber, referenceName, categoryId, profileId, fasterPaymentAllowed}. Also `GET /za/pb/v1/profiles/{profileId}/accounts/{accountId}/beneficiaries` (scope `accounts`). `GET /za/pb/v1/accounts/beneficiarycategories` (scope `beneficiarypayments`) -> {id,isDefault,name} (read-only list). Release note 2024-11-07: approved beneficiaries with "beneficiaryType":"INVESTECAPPROVED".
Limits (community FAQ S2, not official): API payment limit currently R20,000.00 per payment; beneficiary must have been paid at least once via Investec Online before API payments work. Reference-length limits: NOT FOUND. Daily limit: NOT FOUND (only the R20,000 figure). 2FA: S2 says no additional manual verification for normal payments ("does not require additional manual verification"); business profiles with authorisers: see (d).
Synchronous/immediate: the call is synchronous and returns a reference number + PaymentDate/effective date; whether funds settle instantly vs same/next business day is not specified in the spec (INFERRED: normal EFT clearing rules; fasterPayment flag suggests an instant rail when allowed).

## (b) Create a NEW beneficiary – NOT AVAILABLE
Evidence: S1 lists only GET beneficiaries / GET profile beneficiaries / GET beneficiarycategories; no POST/PUT/DELETE for beneficiaries or categories (full path list checked: accounts, balance, transactions, pending-transactions, transfermultiple, paymultiple, beneficiaries, beneficiarycategories, profiles, profile accounts, authorisationsetupdetails, profile beneficiaries, documents, document). Community FAQ S2 explicitly: "Currently, the API does not support direct creation of beneficiaries ... use the Investec Online Portal"; then make at least one payment via Investec Online before paying via API. => must be created manually in Investec Online (documented as of FAQ; spec agrees).
Note: `transfermultiple` takes a raw `beneficiaryAccountId` (own-account transfer between the client's accounts, not third-party beneficiaries) – it is NOT a way to pay new third parties (INFERRED from the example "Trans from PBA to PS"; body also has optional profileId). Scope `transfers`.

## (c) Delay / schedule payment ~24h – NOT AVAILABLE
Evidence: no date/scheduled/future-dated field in paymultiple or transfermultiple request schemas (additionalProperties=false, so unknown fields would be rejected); no scheduled-payment endpoint in the path list; release notes (2020-2026) mention none. Response only reports an "effective date" (server decided). Payments are executed on submit. So any delay (e.g. 24h hold) must be implemented client-side (app queues and calls paymultiple later; token valid only 30 min so mint a fresh token at send time). Authorisation-pending (business) payments have an authorisation window (authPeriodId: "Current Day" or 1-10 working days) – that is an authorisation expiry period, not a scheduled-payment date.

## (d) Authorise payments
Documented (S1): release 2023-09-07 "payment initiation requiring authorisation". `GET /za/pb/v1/profiles/{profileId}/accounts/{accountId}/authorisationsetupdetails` (scope `accounts`) -> numberOfAuthorisationRequired, period[{id,description}] , authorisersListA/B[{authoriserId,name}]. Those IDs go into paymultiple as authoriserAId, authoriserBId, authPeriodId. Response AuthorisationRequired=true means the payment awaits authorisation by the named authorisers (done in Investec Online by them). NO API endpoint to approve/authorise a pending payment found => NOT AVAILABLE. "Typically for Private Business users". Private individual accounts: no authorisation needed in examples.
Auth/credentials (S1): OAuth2 client credentials; POST https://openapi.investec.com/identity/v2/oauth2/token with Basic base64(client_id:client_secret), x-api-key header, grant_type=client_credentials; token valid 30 min. client_id/secret and x-api-key (with chosen scopes) are generated by the user in Investec Online after enrolling for Investec Developer. Scopes: accounts, balances, transactions, transfers, beneficiarypayments, documents(.statements/.taxcertificates). Payments therefore need the key to include `beneficiarypayments` (and `accounts` for account lookup). Whether a separate approval is needed to enable beneficiarypayments scope: NOT FOUND in the spec (UNVERIFIED; the code comment "credential with payments enabled" is consistent with choosing scopes). Community note (S2): programmatic payments only on Private Bank API, not CIB.
Sandbox (S1): base https://openapisandbox.investec.com (same token path); published sandbox credentials exist in the spec; all scopes incl. beneficiarypayments; stateless mock data, repeatable, balances do not change after transfers/payments. Production moves real money.

1. Docstring says "ASSUMPTION (OQ1)... UNVERIFIED" (top) but the comment at line ~119 says "VERIFIED against Investec docs" – internally inconsistent; now verifiable against S1 (mirror) – update wording/cite.
2. create_payment ignores the HTTP-200 body: S1 reports failure via `data.ErrorMessage` (and AuthorisationRequired) – a 200 with non-null ErrorMessage or AuthorisationRequired=true would be treated as success. Callers (payments/pipeline.py ~250, selftest.py ~208) should inspect `data.TransferResponses`/`ErrorMessage`. (Based on spec examples; real error shape for 200s is not documented – INFERRED risk.)
3. Retry adapter: allowed_methods includes POST with status_forcelist 429/500/502/503/504 (total=4). A POST /paymultiple retried after a 5xx/timeout where the bank already executed could DOUBLE-PAY; docs describe no idempotency key. Recommend no automatic retry on payment POSTs (this is a real money-safety risk).
4. Source-account selection: fine (path). No pre-check of R20,000 cap (community), 50-item cap (n/a, single item), or fasterPaymentAllowed; no authoriser fields (only needed for business profiles requiring authorisation) – payments needing authorisation will return AuthorisationRequired and not execute without them.

INFERRED from S1 security blocks: GET beneficiaries requires scope beneficiarypayments).
